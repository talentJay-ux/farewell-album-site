# farewell-album-site

一个可以发到微信里的 H5 相册（竖向滑动、背景音乐、人脸自适应取景），内容**端到端加密**后托管在 GitHub Pages。

仓库是公开的，但公开的只有：页面代码（`index.html`）、Swiper 库、构建脚本，以及 `b/` 下一堆加密后的二进制块和一份不含任何内容的 `manifest.json`。照片、音乐、全部文案（标题、日期、地点、配文、人脸框）都在加密块里，**没有密码什么都看不到** —— 打开页面先输密码，密钥只在浏览器里派生，服务器和仓库从不接触明文。

## 怎么工作

- 输入密码 → 浏览器用 WebCrypto 做 **PBKDF2-SHA256**（60 万次迭代，把密码慢慢"熬"成 256 位主密钥）→ **HKDF-SHA256** 派生出 **AES-256-GCM** 密钥（带完整性校验的对称加密，密码错一位解密就直接失败，不会出现乱码或半张图）。
- 每张照片、每段音乐、`album.json` 各是一个独立的加密块：`12 字节 IV | 密文 | 16 字节校验标签`。页面仍然只加载"当前页 ±2"的图，解密是毫秒级，不影响滑动流畅度；输密码期间就在后台预取封面、音乐和前三张图。
- 密钥派生成功后存进 `localStorage`，同一台手机下次打开免输密码；改过密码重新发布后旧密钥会解密失败，自动回到输密码界面。
- 构建是**确定性**的：块名和 IV 都是用密钥对明文做 HMAC 得到的，内容不变就零 diff，内容变了块名就变（天然 cache busting）。

## 发布 / 更新内容

明文永远只放在本机、被 `.gitignore` 的 `private/`：

```
private/
  album.json      标题、文案、照片列表（路径相对 private/）、"music" 字段指向音乐
  img/*.jpg       每张图三份：原图 / _t 缩略图 / _b 预模糊背景
  music.mp3
```

改好 `private/` 后重新加密并提交：

```sh
ALBUM_PASSWORD='…' node tools/encrypt.mjs      # 读 private/ → 写 b/ 和 manifest.json，删掉不再引用的块
git add -A && git commit -m "update album" && git push
```

密码不通过命令行参数传（会进 shell 历史）：用环境变量 `ALBUM_PASSWORD`，不设的话在终端里隐式输入。

**换密码**：换一个 `ALBUM_PASSWORD` 重新跑 `encrypt.mjs` 即可（整套块都会重新生成）。加 `--new-salt` 会连盐一起换。

**从公开仓库还原明文**（只要有密码）：

```sh
ALBUM_PASSWORD='…' node tools/decrypt.mjs --out ./restored
```

## 安全边界，请知悉

- 加密本身是真的，但**密码强度决定一切**。6 位纯数字只有一百万种可能，拿到仓库的人几分钟就能穷举；想真的防住外人，换一个长密码（`encrypt.mjs` 对密码长度和字符没有限制，锁屏输入框也没有）。
- 块的个数和大小是公开的（能猜到"大约 40 张图、一段音乐"），内容不可见。
- 这个仓库的历史在 2026-10-15 被重写过一次，之前含明文的两次提交已不在任何分支上。GitHub 对已被覆盖的提交对象可能还会缓存一段时间，只有知道原始 commit SHA 的人才可能取到；要 100% 清掉可删库重建或联系 GitHub Support。
